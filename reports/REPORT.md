# Поиск компактной архитектуры ResNet-20 с помощью Effective Rank

## Итоговый отчет по проекту

## Аннотация

В работе исследуется способ автоматического распределения внутренних каналов
между остаточными блоками ResNet-20. В качестве показателя информативности
блока используется эффективный ранг (Effective Rank, ERank), рассчитанный по
активациям или весам сети. Основная идея состоит в том, что блокам с более
высоким эффективным рангом следует сохранить больше каналов, а блоки с низким
рангом можно сузить сильнее.

Эксперимент проведен на CIFAR-10 для двух бюджетов размера модели: `p080`
(около 80% параметров исходной сети) и `p060` (около 60%). Сравнивались
архитектуры `erank_per_image`, `erank_pooled`, `erank_weight`, `uniform` и
`random`. Модели обучались в режимах `scratch` и `finetune`. Для основного
сравнения при бюджете `p060` выполнено три независимых запуска: `seed1`,
`seed2` и `seed3`.

Лучший средний результат среди компактных моделей показала архитектура
`p060_erank_per_image_scratch`: **91,46 ± 0,34%** на тестовой выборке при
**162 790 параметрах**, то есть при сохранении 59,75% параметров `baseline`.
Средняя потеря относительно полной ResNet-20 составила 0,65 процентного пункта.
Архитектура `erank_per_image` превзошла `erank_pooled` во всех трех запусках,
но ее преимущество над `uniform` оказалось небольшим и не повторилось в каждом
`seed`. Поэтому основная гипотеза подтверждена частично: ERank позволяет
построить качественную компактную модель, однако имеющихся запусков пока
недостаточно, чтобы утверждать безусловное превосходство над равномерным
сужением.

## 1. Термины, обозначения и названия режимов

В отчете сохранены названия, которые используются в коде, конфигурациях и
каталогах результатов. Это исключает неоднозначность при сопоставлении текста
отчета с файлами проекта.

### 1.1. Названия моделей и режимов

| Термин | Определение |
|---|---|
| `baseline` | Исходная полная ResNet-20. Ее внутренние ширины не уменьшались. Результаты `baseline` служат точкой отсчета для всех компактных моделей. |
| `p080` | Бюджет, при котором компактная модель должна сохранить примерно 80% параметров `baseline`. |
| `p060` | Более строгий бюджет: компактная модель должна сохранить примерно 60% параметров `baseline`. |
| `erank_per_image` | ERank рассчитывается отдельно для активаций каждого изображения, после чего значения усредняются. Полученные оценки используются для распределения ширины между блоками. |
| `erank_pooled` | Активации всей проверочной выборки объединяются в общую статистику, и ERank рассчитывается по объединенным центрированным данным. |
| `erank_weight` | ERank рассчитывается не по активациям, а по матрице весов первого сверточного слоя каждого остаточного блока. |
| `uniform` | Все блоки сужаются примерно в одной пропорции. Архитектура подбирается так, чтобы число параметров было близко к размеру ERank-модели. |
| `random` | Ширины распределяются между блоками случайно при соблюдении ограничений и заданного бюджета параметров. |
| `scratch` | Обучение компактной модели с нуля. Все веса получают новую случайную инициализацию; веса `baseline` не используются. |
| `finetune` | Дообучение компактной модели после переноса части весов из `baseline`. В данном проекте переносимые каналы выбирались по L1-норме фильтров. |
| `seed1`, `seed2`, `seed3` | Независимые запуски с разными начальными случайными состояниями. `seed` влияет на инициализацию весов, порядок обучающих данных и разбиение исходной обучающей части CIFAR-10. |
| `checkpoint` | Файл с сохраненным состоянием модели. `best.pt` содержит модель с лучшей точностью на проверочной выборке, `last.pt` - состояние после последней эпохи. |

### 1.2. Термины, связанные с архитектурой

| Термин | Определение |
|---|---|
| Канал | Один компонент многоканального представления признаков. Увеличение числа каналов обычно повышает вычислительную емкость блока, но также увеличивает размер и стоимость модели. |
| Активации | Числа, которые формируются внутри сети после применения слоя к входным данным. В этой работе анализировались выходы `Conv1 -> BN -> ReLU` девяти остаточных блоков. |
| Внутренняя ширина | Число каналов между первым и вторым сверточными слоями остаточного блока. Именно эта величина изменялась при построении компактных моделей. |
| Сингулярные значения | Числа, характеризующие вклад независимых направлений в матрице активаций или весов. Они используются для расчета ERank. |
| Effective Rank, ERank | Непрерывная оценка эффективной размерности матрицы. В отличие от обычного ранга учитывает не только число ненулевых направлений, но и распределение их относительной силы. |
| Архитектурный поиск | Процедура определения внутренних ширин девяти блоков по выбранному критерию и ограничению на общее число параметров. |

### 1.3. Метрики

| Метрика | Определение |
|---|---|
| `accuracy` | Доля изображений, для которых модель правильно определила класс. В таблицах приведена в процентах. |
| `loss` | Значение функции ошибки Cross-Entropy. Используется при обучении; меньшее значение обычно соответствует более уверенным правильным предсказаниям. |
| `parameters` | Число обучаемых параметров модели. Характеризует размер архитектуры, но не полностью определяет ее скорость. |
| `MACs` | Число операций умножения со сложением. В проекте рассчитывается для одного пакета из 128 изображений. |
| `FLOPs` | Приближенное число операций с плавающей точкой. В отчетах проекта принято приближение `FLOPs ≈ 2 × MACs`. |
| `latency_median_ms` | Медианное время одного прохода модели для пакета. Медиана слабо зависит от отдельных случайных задержек. |
| `latency_p90_ms` | Значение задержки, быстрее которого завершились 90% измерений. Эта метрика показывает стабильность времени выполнения. |
| `images_per_second` | Пропускная способность: сколько изображений модель обрабатывает за секунду при заданном размере пакета. |
| `peak_cuda_memory_bytes` | Максимальный объем памяти CUDA, зафиксированный во время измерения. |
| Стандартное отклонение | Показатель разброса результатов между `seed1`, `seed2` и `seed3`. В записи `91,46 ± 0,34%` число 0,34% показывает наблюдаемый разброс трех запусков. |
| Процентный пункт | Абсолютная разница между двумя значениями точности. Например, 92,11% и 91,46% различаются на 0,65 процентного пункта. |

## 2. Постановка задачи

### 2.1. Проблема

Стандартная ResNet-20 использует заранее заданное число каналов в каждом
остаточном блоке. Такое распределение удобно и симметрично, но не обязательно
оптимально. Разные блоки обрабатывают признаки разной сложности и могут иметь
различную фактическую размерность внутренних представлений. Следовательно,
часть блоков может содержать избыточное число каналов, тогда как для других
блоков сильное сужение окажется критичным.

Простое уменьшение всех ширин в одной пропорции не учитывает эти различия.
Архитектурный поиск по ERank должен ответить на вопрос, можно ли распределить
тот же бюджет параметров более обоснованно.

### 2.2. Цель

Цель работы - проверить, позволяет ли Effective Rank построить компактную
ResNet-20 с меньшим числом параметров и вычислений при ограниченной потере
точности на CIFAR-10.

### 2.3. Исследовательские вопросы

1. Какая из оценок - `erank_per_image`, `erank_pooled` или `erank_weight` -
   формирует наиболее успешное распределение ширин?
2. Превосходит ли ERank простую архитектуру `uniform` при одинаковом бюджете?
3. Дает ли осмысленное распределение ширин преимущество над `random`?
4. Как уменьшение параметров влияет на `MACs`, реальную задержку, пропускную
   способность и память CUDA?
5. Что эффективнее для компактной архитектуры: `scratch` или `finetune`?
6. Сохраняются ли выводы при переходе от бюджета `p080` к более строгому
   бюджету `p060`?

### 2.4. Рабочая гипотеза

Если ERank отражает сложность признакового пространства конкретного блока, то
распределение ширин пропорционально ERank должно обеспечивать более высокую
точность, чем `uniform` и `random`, при близком числе параметров.

## 3. Данные и исходная модель

### 3.1. CIFAR-10

CIFAR-10 содержит 60 000 цветных изображений размером 32 × 32 пикселя,
разделенных на десять классов. Официальная обучающая часть содержит 50 000
изображений, официальная тестовая часть - 10 000.

В проекте данные использовались следующим образом:

| Часть данных | Число изображений | Назначение |
|---|---:|---|
| Обучающая | 45 000 | Обновление весов модели |
| Проверочная | 5 000 | Выбор `best.pt`, расчет активаций и архитектурный поиск |
| Тестовая | 10 000 | Единственная финальная оценка уже выбранного `checkpoint` |

Разделение первых 50 000 изображений выполнялось детерминированно для каждого
`seed`. При обучении применялись случайная обрезка с полем 4 пикселя,
горизонтальное отражение и нормализация. Для проверки и теста использовалась
только нормализация. Тестовая выборка не влияла ни на обновление весов, ни на
выбор эпохи, ни на построение архитектуры.

### 3.2. ResNet-20

Исходная модель `baseline` - ResNet-20 для CIFAR-10 с девятью остаточными
блоками. Внутри каждого блока используется последовательность:

```text
вход -> Conv1 -> BN1 -> ReLU -> Conv2 -> BN2 -> сложение с residual-связью
```

В стандартной архитектуре внутренние ширины девяти блоков равны:

```text
[16, 16, 16, 32, 32, 32, 64, 64, 64]
```

В проекте изменяется только промежуточная ширина между `Conv1` и `Conv2`.
Внешние размеры блоков сохраняются, поэтому residual-связи остаются
совместимыми. Такой подход позволяет сравнивать разные распределения внутренних
ресурсов, не меняя общую структуру ResNet-20.

## 4. Метод Effective Rank

### 4.1. Математическое определение

Пусть для некоторого блока сформирована матрица активаций $X$, а ее сингулярные
значения равны $\sigma_1, \sigma_2, \ldots, \sigma_n$. Сначала они
нормализуются:

$$
p_i = \frac{\sigma_i}{\sum_j \sigma_j}.
$$

Затем рассчитывается энтропия распределения:

$$
H(p) = -\sum_i p_i \ln p_i.
$$

Эффективный ранг определяется как:

$$
r_{eff}(X) = \exp(H(p)).
$$

Если вклад распределен по многим направлениям равномерно, энтропия и ERank
будут высокими. Если почти вся энергия сосредоточена в нескольких направлениях,
ERank будет низким. В отличие от обычного ранга, очень слабое направление не
получает такой же вес, как сильное.

Важно: ERank не равен гарантированно необходимому числу каналов. Это показатель
структуры данных, который в данной работе используется как эвристика для
распределения ограниченного бюджета.

### 4.2. `erank_per_image`

Для каждого изображения активации блока рассматриваются отдельно. Пространственные
позиции образуют наблюдения, а каналы - признаки. После расчета ERank для каждого
изображения значения усредняются по проверочной выборке.

Такой вариант сохраняет локальную структуру отдельных примеров. Сложность
представления одного изображения не смешивается с различиями между изображениями
разных классов.

### 4.3. `erank_pooled`

Активации всех изображений объединяются статистически, после чего данные
центрируются и рассчитывается один ERank на блок. Полная матрица активаций не
хранится в памяти: по пакетам накапливаются число наблюдений, сумма векторов и
матрица $X^T X$.

`erank_pooled` оценивает общую размерность признакового пространства всей
проверочной выборки. Однако эта оценка одновременно учитывает внутриклассовые
признаки и различия между изображениями, поэтому ее смысл отличается от
`erank_per_image`.

### 4.4. `erank_weight`

В этом варианте ERank рассчитывается по матрице весов `Conv1` каждого блока.
Для вычисления не нужны активации и набор изображений. Такой критерий проще,
но он описывает структуру параметров, а не фактически используемые моделью
представления.

В проведенном эксперименте после округления и согласования бюджета
`erank_weight` сформировал те же ширины, что и `erank_pooled`. Поэтому отдельное
обучение идентичной архитектуры не выполнялось: результаты
`erank_pooled` одновременно представляют этот вариант на данном наборе данных.

### 4.5. Преобразование ERank в ширины

Значения ERank задают относительное распределение ресурсов между девятью
блоками. Затем общий коэффициент масштаба подбирается так, чтобы фактическое
число параметров модели приблизилось к заданному бюджету.

При построении архитектур соблюдались ограничения:

- минимальная внутренняя ширина ERank- и `random`-блока - 4 канала;
- ширина не превышает соответствующую ширину `baseline`;
- для ERank и `random` ширины округляются до четных значений;
- бюджет контролируется по реальному числу параметров всей модели, а не по
  простой сумме каналов;
- `uniform` выбирается из целочисленной и четной сеток так, чтобы лучше
  соответствовать целевому числу параметров.

Последний пункт важен: два распределения с одинаковой суммой ширин могут иметь
разное число параметров и разное число операций, поскольку каналы в ранних и
поздних блоках имеют разную вычислительную стоимость.

## 5. Контрольные архитектуры и честность сравнения

### 5.1. `uniform`

`uniform` проверяет, действительно ли ERank полезен как способ распределения
каналов. Если сложная ERank-архитектура не превосходит равномерное сужение того
же размера, практическая ценность архитектурного поиска ограничена.

### 5.2. `random`

`random` проверяет более слабую альтернативу: может ли любое неравномерное
распределение случайно дать сопоставимый результат. Для каждого бюджета была
сформирована одна случайная архитектура. Поэтому сравнение с `random` является
предварительным: для полноценной статистики нужны несколько независимо
сгенерированных случайных архитектур.

### 5.3. Согласование размера

Для `p060` число параметров находится в диапазоне от 162 470 до 162 790, то
есть максимальная разница между компактными моделями составляет всего 320
параметров, или около 0,12% размера `baseline`. Для `p080` диапазон составляет
218 226–219 062 параметра.

Таким образом, различия точности нельзя объяснить существенным преимуществом
одной модели по размеру. При этом равное число параметров не означает равное
число MACs: расположение каналов внутри сети влияет на вычислительную стоимость.

## 6. Протокол эксперимента

### 6.1. Обучение `scratch`

| Параметр | Значение |
|---|---:|
| Оптимизатор | SGD с momentum и Nesterov |
| Число эпох | 160 |
| Начальный learning rate | 0,1 |
| План изменения learning rate | CosineAnnealing |
| Momentum | 0,9 |
| Weight decay | 0,0005 |
| Batch size | 128 |
| AMP на CUDA | включен |
| Критерий выбора `best.pt` | максимальная `validation accuracy` |

Все сравниваемые `scratch`-модели использовали один протокол. Отличались только
внутренние ширины и `seed`. Это необходимо, чтобы изменение результата можно
было связывать с архитектурой, а не с разными настройками обучения.

### 6.2. Подготовка `finetune`

ERank определяет число каналов в блоке, но не указывает, какие именно каналы
полной модели нужно перенести. Для решения этой отдельной задачи использовалась
L1-норма фильтров `Conv1`:

1. Фильтры `Conv1` упорядочивались по L1-норме.
2. Выбиралось требуемое число наиболее крупных фильтров.
3. Те же индексы применялись к выходам `Conv1`, параметрам и статистикам `BN1`
   и входным каналам `Conv2`.
4. Полученная компактная модель дообучалась 30 эпох с начальным learning rate
   0,01.

Одинаковое правило переноса использовалось для `erank_per_image`,
`erank_pooled`, `uniform` и `random`. Следовательно, сравнение режимов
`finetune` отражает различия архитектур, а не разные способы выбора каналов.

### 6.3. Повторные запуски

Полное сравнение по трем запускам выполнено для:

- `baseline`;
- `p060_erank_per_image_scratch`;
- `p060_erank_pooled_scratch`;
- `p060_uniform_scratch`.

Для `seed2` и `seed3` использовались те же ширины, которые были найдены по
`baseline_seed1`. Повторялось обучение модели, но не весь архитектурный поиск.
Такой дизайн проверяет устойчивость выбранной архитектуры к инициализации и
порядку данных, но не проверяет устойчивость самого расчета ERank.

### 6.4. Измерение производительности

Для всех архитектур использовались одинаковые условия:

- устройство CUDA;
- batch size 128;
- 50 прогревочных проходов;
- 200 измеряемых проходов;
- одинаковая программная и аппаратная среда.

Измерялись `MACs`, `latency_median_ms`, `latency_p90_ms`,
`images_per_second` и `peak_cuda_memory_bytes`. Производительность зависит от

интерпретировать вместе с относительным сравнением моделей в одном окружении.

## 11. Сравнение `scratch` и `finetune`

В таблице сравнивается `seed1`. Положительная разница означает улучшение после
`finetune`, отрицательная - ухудшение относительно `scratch`.

| `p060` | `erank_pooled` | 90,95% | 91,17% | +0,22 п.п. |
| `p060` | `random` | 91,04% | 91,00% | −0,04 п.п. |
| `p080` | `erank_per_image` | 92,22% | 92,07% | −0,15 п.п. |
| `p080` | `uniform` | 91,95% | 92,23% | +0,28 п.п. |
| `p080` | `erank_pooled` | 91,72% | 91,83% | +0,11 п.п. |
| `p080` | `random` | 91,81% | 91,66% | −0,15 п.п. |

Эффект `finetune` не является систематическим. При `p060` он помог двум
ERank-архитектурам, но ухудшил `uniform`. При `p080` максимальное улучшение

быть неоптимальными для части архитектур.

На основании одного `seed` нельзя сделать вывод о принципиальном преимуществе
`scratch` или `finetune`. Поэтому основной результат проекта основан на
`scratch` и повторных запусках `p060`.

## 12. Обсуждение результатов

### 12.1. Почему `erank_per_image` оказался лучше `erank_pooled`

Оба метода используют активации одной модели, но измеряют разные свойства.
`erank_per_image` оценивает внутреннюю размерность представления отдельного
изображения, после чего усредняет оценки. `erank_pooled` строит общую статистику
по всем изображениям и поэтому включает различия между примерами и классами.

Результаты показывают, что для распределения внутренних ширин ResNet-20 более
полезной оказалась локальная оценка на уровне изображения. Возможная причина:
она точнее отражает число одновременно используемых направлений внутри блока,
не увеличивая оценку за счет разнообразия всей выборки.

Это объяснение является интерпретацией, а не доказанным механизмом. Для его
проверки потребуется анализ ERank по классам, распределений индивидуальных
рангов и связи ранга каждого блока с чувствительностью точности к удалению
каналов.

### 12.2. ERank против `uniform`

Средняя точность `p060_erank_per_image_scratch` выше `p060_uniform_scratch` на
0,28 процентного пункта. Одновременно `uniform` требует меньше MACs, имеет
меньшую задержку и ниже расход памяти. Поэтому выбор зависит от целевой функции:

- если приоритетом является максимальная точность в заданном параметрическом
  бюджете, предпочтительнее выглядит `erank_per_image`;
- если приоритетом является реальная скорость вывода, `uniform` в текущем
  эксперименте выгоднее;
- если нужно совместно оптимизировать точность и задержку, одного ограничения
  на параметры недостаточно - бюджет должен учитывать MACs или измеренную
  latency.

### 12.3. Параметры не равны вычислительной стоимости

`erank_per_image`, `uniform` и `erank_pooled` имеют практически одинаковый
размер, но различаются по MACs почти на 0,52 млрд операций на пакет. Причина в
том, что одинаковое число каналов имеет разную стоимость в разных местах сети.

Этот результат показывает ограничение параметрического бюджета. Для
практического применения архитектурный поиск целесообразно расширить до
многокритериальной задачи:

$$
\text{максимизировать accuracy при ограничениях на parameters, MACs и latency}.
$$

### 12.4. Проверка исходной гипотезы

Гипотеза подтверждена частично.

- Подтверждено, что ERank способен сформировать компактную архитектуру с
  небольшой потерей точности относительно `baseline`.
- `erank_per_image` устойчиво превзошел `erank_pooled` в трех запусках `p060`
  и показал лучший результат `seed1` при `p080`.
- Превосходство над `uniform` пока не доказано: средний выигрыш мал, а в одном
  из трех запусков `uniform` оказался лучше.
- Для `random` недостаточно одной архитектуры и одного запуска, чтобы получить
  надежное статистическое сравнение.

## 13. Ограничения эксперимента

1. **Малое число повторов.** Три `seed` выполнены только для основного сравнения
   `p060`. Для `p080`, `random` и `finetune` доступен один запуск.
2. **Фиксированная найденная архитектура.** В `seed2` и `seed3` повторялось
   обучение, но ERank не пересчитывался по новой `baseline`. Поэтому проверена
   устойчивость архитектуры, а не полного алгоритма поиска.
3. **Одна `random`-архитектура.** Случайное распределение само является
   случайной величиной. Для корректного baseline нужно несколько разных
   `random`-архитектур на каждый бюджет.
4. **Одна модель и один набор данных.** Выводы относятся к ResNet-20 и CIFAR-10.
   Их нельзя автоматически переносить на ResNet-18, CIFAR-100, ImageNet или
   трансформеры.
5. **Одна итерация архитектурного поиска.** После обучения компактной модели
   ERank не пересчитывался повторно. Итеративное сужение может дать другой
   результат.
6. **Один способ переноса каналов.** В `finetune` использовалась L1-норма.
   Другой способ выбора фильтров может изменить итог.
7. **Зависимость latency от оборудования.** Абсолютное время зависит от GPU,
   CUDA, PyTorch, размера batch и фоновой нагрузки.
8. **Нет статистического теста.** Среднее и стандартное отклонение описывают
   наблюдаемые запуски, но не доказывают статистическую значимость различий.

## 14. Направления дальнейшей работы

1. Выполнить `p080` для `seed2` и `seed3`.
2. Сгенерировать несколько независимых `random`-архитектур для каждого бюджета.
3. Повторить полный цикл поиска ERank для каждой `baseline_seedN`, а не только
   переобучать фиксированные ширины.
4. Сравнить ERank с методами L1 pruning, Taylor pruning, HRank и Network
   Slimming при одинаковых бюджетах.
5. Добавить бюджет по MACs или измеренной latency, а не только по parameters.
6. Проверить метод на CIFAR-100 и более крупной архитектуре, например ResNet-18.
7. Исследовать ERank по отдельным классам и связь ERank блока с падением

8. Для `finetune` проверить несколько learning rate, длительность дообучения и
   альтернативные правила выбора переносимых каналов.

## 15. Итоговые выводы

1. `p060_erank_per_image_scratch` уменьшает число параметров ResNet-20 с
   272 474 до 162 790, то есть на 40,25%, и достигает средней тестовой точности
   **91,46 ± 0,34%**.
2. Потеря относительно `baseline` составляет **0,65 процентного пункта**, что
   показывает возможность существенного уменьшения модели без сопоставимого
   падения качества.
3. `erank_per_image` превосходит `erank_pooled` во всех трех запусках `p060`;
   средняя разница составляет **0,59 процентного пункта**.
4. Преимущество `erank_per_image` над `uniform` составляет в среднем только
   **0,28 процентного пункта** и не воспроизводится в каждом `seed`. Этот вывод
   требует дополнительных запусков.
5. `uniform` является лучшим вариантом по скорости: медианная latency ниже
   `baseline` на 17,40%, а пропускная способность выше на 21,07%.
6. Сокращение параметров не гарантирует пропорционального уменьшения MACs,
   latency и памяти. Расположение каналов не менее важно, чем их общее число.
7. `finetune` не показал постоянного преимущества над `scratch`; его эффект
   зависел от архитектуры и бюджета.
8. На текущем этапе ERank следует рассматривать как перспективный критерий
   распределения ширин, а не как универсально доказанный способ превосходства
   над простым `uniform`.
